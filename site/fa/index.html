از یک اپ یا کل سرور بک‌آپ بگیرید. روی سرور جدید فقط یک دستور بزنید. همه‌چیز روشن و بررسی‌شده می‌رسد.

همراه اپ شما چه می‌آید

یک دامنه را از لیست انتخاب کنید. هر چیزی که اپ برای کار کردن لازم دارد همراهش می‌آید و سرور جدید آن را با خود Coolify روشن می‌کند.

داده‌ها، در حالی که اپ کار می‌کند

volumeها، پوشه‌ها و فایل‌ها. کانتینرها فقط چند ثانیه‌ی کپی pause می‌شوند. دیتابیس‌ها هیچ‌وقت.

dump واقعی دیتابیس‌ها

PostgreSQL، MySQL و MariaDB با pg_dumpall و mysqldump ذخیره و روی سرور جدید با همان image بارگذاری می‌شوند.

همه‌ی تنظیمات Coolify

پروژه‌ها، environmentها، متغیرها، storageها، تگ‌ها، تسک‌ها و بک‌آپ‌های زمان‌بندی‌شده. رمزها با کلید سرور جدید دوباره رمزنگاری می‌شوند.

وابستگی‌ها خودشان پیدا می‌شوند

اپ را انتخاب کنید. Postgresی که پشت DATABASE_URL آن است پیدا و پیشنهاد می‌شود.

بدون build دوباره روی سرور جدید

همان imageهایی که اپ‌ها با آن اجرا می‌شوند منتقل می‌شوند. اپ‌های Docker Compose بدون clone و build از همان‌ها روشن می‌شوند؛ مهم‌تر از همه روی اینترنت کند.

دامنه‌ها، آخر کار

درست قبل از روشن شدن، هر دامنه را نگه دارید یا دامنه‌ی جدید بنویسید. Coolify برچسب‌های پروکسی را به‌روز می‌کند.

کل انتقال، صفحه به صفحه

صفحه‌های واقعی از انتقال به یک Coolify 4.3.23 تازه‌نصب با نسخه‌ی منتشرشده‌ی برنامه. یک مرحله و بعد یک صفحه را انتخاب کنید. منوی برنامه انگلیسی است؛ اسم دقیق هر گزینه را این‌جا می‌بینید.

روی سرور قدیم

بک‌آپ بگیرید و به اشتراک بگذارید

با SSH و کاربر root یا کاربری که sudo دارد وارد سرور قدیم شوید و بزنید:

curl -fsSL https://raw.githubusercontent.com/mtalavi/coolify-mirror/main/install.sh | sudo sh
  1. What do you want to do?گزینه‌ی Back up apps
  2. Which app should be backed up?با کلیدهای جهت روی اپ بروید و Enter. چند اپ: روی هر کدام Space و بعد Enter.
  3. Also back up what they depend on?Yes
  4. Backup settingsRecommended
  5. How should the other server get this backup?Share a link through Coolify's proxy on port 443
  6. On the other Coolify server, run this one commandخط سبزی را که با curl شروع می‌شود کپی کنید.

تا سرور جدید دانلود کند این پنجره را باز بگذارید، یا b بزنید تا اشتراک ۲۴ ساعت در پس‌زمینه بماند.

روی سرور جدید

خط را Paste کنید و Yes بزنید

با SSH وارد سرور جدید شوید و خطی را که کپی کردید Paste کنید. شبیه این است:

curl -fsSL https://raw.githubusercontent.com/mtalavi/coolify-mirror/main/install.sh | sudo sh -s restore 203.0.113.10/hi4i-2dzx-hmeg-42qp-palx-52s7-zq example
  1. Getting the backupنصب، دانلود و بررسی همه‌ی داده‌ها. هنوز هیچ تغییری نمی‌کند.
  2. Restore these resources into this Coolify?فهرست را بخوانید و Yes بزنید.
  3. DomainsEnter یعنی همان دامنه بماند؛ یا دامنه‌ی جدید را بنویسید.
  4. Rebuild N application(s) once now?Yes ثابت می‌کند deployهای بعدی هم کار می‌کنند. اینترنت کند: No.
  5. Restore complete · everything verifiedتمام. Coolify جدید را باز کنید.

سؤال rebuild فقط برای اپ‌هایی می‌آید که Coolify از Git می‌سازد. اگر برنامه روی این سرور نصب است: sudo coolify-mirror و بعد Restore a backup.

انتقال‌های واقعی

سه اجرا روی Coolify 4.3.23 واقعی، با چیزهایی که اندازه گرفته شد.

یک اپ واقعی Docker Compose با ۷ سرویس، Postgres، ۶ volume و یک اسکریپت build روی میزبان، به سروری با اینترنت کند منتقل شد.

  • یک deployment ثبت‌شده با شناسه‌های سرور جدید

پنج نوع اپ، صفر دخالت دستی

۰کار دستی

اپ Compose با اسکریپت build روی میزبان و builder نام‌دار، اپ Dockerfile، اپ image، WordPress با MariaDB و Postgres. همان secretها، داده‌ی volume و ردیف‌های دیتابیس (md5) مبدأ، همه‌ی دامنه‌ها در حال جواب، و یک rebuild کامل روی سرور جدید.

همین آموزش بالا: یک اپ و Postgres آن از پورت 443 به یک Coolify تازه‌نصب منتقل شد. دانلود ۴۷٫۵ مگابایت و بررسی آن در شبکه‌ی آزمایشگاه یک ثانیه طول کشید.

ساخته‌شده تا چیزی از دست نرود

رمزنگاری از اول تا آخر

بک‌آپ یک فایل رمزشده با age است. با HTTPS و گواهی‌ای منتقل می‌شود که کد اشتراک آن را pin کرده. HTTP ساده هرگز.

بررسی قبل از هر تغییر

نسخه‌ی یکسان Coolify، فضای دیسک، اعتبارسنجی bundle با خود Coolify، تداخل‌ها، و یک import آزمایشی در تراکنشی که برگردانده می‌شود.

برگشت (Rollback)

اگر import شکست بخورد، هر چیزی که ساخته شده پاک می‌شود. ریستور کامل دیتابیس و .env قبلی Coolify را برمی‌گرداند.

هیچ چیز پنهانی پاک نمی‌شود

volume موجود داده‌اش را با اسم <name>.cm-old-<time> نگه می‌دارد. پوشه‌های جایگزین‌شده تا وقتی خودتان پاک کنید می‌مانند.

هر بار فقط یک اجرا

یک قفل جلوی دو بک‌آپ یا ریستور هم‌زمان را می‌گیرد. کانتینرهای pause‌شده همیشه ادامه می‌دهند، حتی بعد از ctrl+c.

آماده‌ی آپدیت‌های Coolify

هر اجرا بخش‌هایی از Coolify را که لازم دارد بررسی می‌کند. یک تست روزانه اپ‌های واقعی را بین دو نصب تازه‌ی هر نسخه‌ی جدید Coolify جابه‌جا می‌کند.

پشت صحنه

یک فایل از یک سرور به سرور دیگر می‌رود. در هر طرف این اتفاق می‌افتد.

سرور قدیم

  1. Coolify rows of the picked apps
  2. volumes, files, images, dumps
  3. Coolify's own transfer bundle
  4. tar, zstd, age: backup.cmb
HTTPS روی پورت 443 با گواهی pin‌شده

سرور جدید

  1. download, resume, verify
  2. preflight and trial import
  3. restore and import, new IDs
  4. start through Coolify, verify

خود برنامه

  • Go 1.26، یک فایل اجرایی برای لینوکس amd64 و arm64
  • Bubble Tea، huh و Lip Gloss برای رابط ترمینال
  • رمزنگاری age (رمز با scrypt) و فشرده‌سازی zstd

داخل Coolify

  • Server Transfer bundle (schema_version 1) که کد خود Coolify می‌سازد و بررسی می‌کند
  • رمزها با APP_KEY قدیمی باز و با کلید جدید دوباره رمزنگاری می‌شوند
  • Traefik TLS passthrough اشتراک را روی پورت 443 می‌برد

انتشار

  • GitHub Actions هر نسخه و SHA-256 آن را می‌سازد
  • نصب‌کننده قبل از اجرا checksum را بررسی می‌کند
  • تست روزانه یک انتقال کامل روی هر نسخه‌ی جدید Coolify

پرسش‌ها

با کدام نسخه‌های Coolify کار می‌کند؟

Coolify 4.3.x، و هر دو سرور باید دقیقاً یک نسخه باشند. برنامه در شروع می‌گوید این نسخه تست شده یا نه. اگر نسخه‌ها فرق داشته باشند، می‌گوید کدام سرور را آپدیت کنید.

سرور قدیم هنگام بک‌آپ از کار می‌افتد؟

نه. با تنظیمات Recommended کانتینرها فقط چند ثانیه‌ای که کپی volumeشان طول می‌کشد pause می‌شوند و دیتابیس‌ها در حال کار dump می‌شوند. روی سرور قدیم چیزی پاک نمی‌شود.

سرور جدید می‌تواند پروژه‌های دیگری هم داشته باشد؟

بله. بک‌آپ اپ‌ها با Coolify جدید ادغام می‌شود و هر چه آن‌جاست می‌ماند. اپی که از قبل هست را می‌شود به‌صورت کپی ریستور کرد یا رد کرد. بک‌آپ کل سرور فقط روی Coolify تازه و خالی می‌نشیند.

سرور جدید به سرور قدیم وصل نمی‌شود.

پورت 443 سرور قدیم بسته است. روی سرور قدیم q بزنید، بعد Share a saved backup، همان بک‌آپ، و Share a link on port 8123. پورت 8123 را در فایروال دیتاسنتر هم باز کنید و دستور جدیدی را که نشان می‌دهد روی سرور جدید بزنید.

SSH وسط دانلود قطع شد.

اشتراک سرور قدیم را باز نگه دارید و همان دستور را دوباره بزنید؛ دانلود از همان‌جا ادامه پیدا می‌کند. روی سرورهای بزرگ برنامه را داخل tmux اجرا کنید.

سرور جدید به GitHub دسترسی ندارد.

سرور قدیم یک دستور دوم هم نشان می‌دهد که برنامه را از خود سرور قدیم و از همان اتصال pin‌شده دانلود می‌کند.

چه چیزهایی منتقل نمی‌شود؟

ریسورس‌های روی سرورهای remote، preview deploymentها و Swarm. webhookها و DNS تا وقتی خودتان عوض نکنید به سرور قدیم اشاره می‌کنند. بین معماری‌های مختلف CPU، Coolify اپ‌ها را دوباره build می‌کند.

این ابزار رسمی Coolify است؟

نه. یک پروژه‌ی متن‌باز مستقل با لایسنس MIT است و به Coolify یا coolLabs وابسته نیست.
